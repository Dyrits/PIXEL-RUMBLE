1 · Give “a duel happened” one home

Strong

Files: views.js (quickPick, placementPick, setDeltaNodes) · app.js (applyDuel, undoLast) · engine.js (duel, replayBattles) · sync.js (push)

Problem: One quick duel spans five files: views orchestrate locking/sound/DOM classes, app.js applyDuel mutates the ladder, engine duel moves ratings, save() persists, sync pushes. Worse, app.js:140 re-implements the preA/preB undo snapshot that replayBattles also builds (engine.js:514) — if they diverge, undo breaks while every test stays green. The concept has no module; locality is zero.

Solution: One battle-constructor in engine.js (build the battle record with its snapshots, apply it to records) that both the live path and the replay path call; app.js shrinks to “ask the engine, persist, notify.”

Benefits: locality — the duel rules (K-factor, snapshots, hist cap) sit in one place; leverage — the same constructor serves live duels, undo, sync merge, and the server’s global replay; tests — engine.test.js then covers the exact code the browser runs.

  R[engine replayBattles\nsnapshot v2] --> M[mergeStores]
  A -.diverges.-. R

2 · Split the PR facade into selectors and commands

Strong

Files: app.js:882-948 (window.PR, ~60 members) · views.js (consumes 41, writes through 6)

Problem: PR is a shared-memory hole, not an interface: views write app state directly (pr.duelMode = key, pr.quick.locked = true, filters.era = …), and app.js re-enters views by synthetically clicking rendered covers (PRViews.__placePick) — the DOM is a control-flow seam. The deletion test fails: deleting PR scatters the same coupling rather than concentrating it.

Solution: Read-only selectors for rendering plus named commands (PR.pickQuick(i), PR.skipPair(), PR.answerPlacement(better)) that own the mode flows views currently orchestrate. Views render state; they stop mutating it.

Benefits: depth — a small command interface hides duel-mode flow; leverage — keyboard handling (app.js) and clicks (views.js) cross the same seam; locality — a mode bug has one address. Testability: flows become callable without a DOM.

Before — two-way coupling

  V[views.js] -- writes state --> PR[PR facade ~60 members]
  PR -- reads --> V
  A[app.js] -- synthetic clicks --> V

After — one-way through commands

flowchart LR
  V[views render] -- commands --> A[app flows]
  K[keyboard] -- commands --> A
  A -- selectors --> V

3 · One owner for the store document

Worth exploring

Files: engine.js (validStore, mergeStores) · app.js (loadStore, save, replaceStore, ensureRecs) · sync.js (JSON.stringify diffing) · server/src/sync.ts (parseStoreDoc, StoreDoc, rater counting)

Problem: The store’s shape is everybody’s implementation detail. The milestone review already single-sourced the validity predicate; the remaining copies (app.js lifecycle rules, sync.js byte-diff, server battle extraction) each know document internals. Also ensureRecs mutates and saves from read paths — touching the store for a read silently schedules a sync push.

Solution: A store module (client-side, engine-adjacent) owning parse / validate / repair / diff; app.js consumes it, sync.js asks it “did anything change?”, the server keeps only its JSON+size validation. Reads stop writing: repairs collect explicitly and save once.

Benefits: a store-shape or version bump touches one module instead of four coordinated edits where a miss silently rejects a device’s ladder; sync stops diffing by string; the hidden write-on-read seam disappears.

Before — four owners

  APP[app.js lifecycle] --- ST[store shape]
  ENG[engine merge] --- ST
  SYN[sync.js diff] --- ST
  SRV[server parse] --- ST

After — one deep module

  STORE[store module\nparse · validate · repair · diff]
  APP[app.js] --> STORE
  SYN[sync.js] --> STORE
  SRV[server JSON+size] -- JSON --> STORE

4 · Chrome module: one toast, one fetch helper

Worth exploring

Files: app.js:451, auth.js, sync.js (three toast copies — one already drifted on timers before the review fixed it) · auth.js:11, sync.js:22 (two fetch helpers)

Problem: Shallow duplicates that fail the deletion test — deleting any copy changes nothing. The timer drift the review caught is exactly the failure mode copies invite.

Solution: A tiny chrome module (loaded before auth/sync): toast(msg) and api(path, opts). Auth and sync keep their DOM/state logic.

Benefits: locality for future chrome (offline banner, sync status); one toast timeline. Cheap: an afternoon, no behavior change.

5 · Serve the Global ranking complete

Speculative

Files: views.js global() · sync.js PRGlobal · server/src/sync.ts globalRanking

Problem: The Global tab reaches sideways: PRGlobal.get lives in sync.js (a module about syncing your ladder, not about rankings), and views recompute tiers client-side — a third tier computation site. The deletion test fails PRGlobal: it is a one-method forwarding module.

Solution: Have the server compute tiers alongside ratings (it owns computeTiers inputs already), and move the fetch+cache next to the view or into a small ranking client. Speculative because the global payload may grow sorting/filtering anyway (deferred scope), which would reshape this interface.

Benefits: one tier rule; views render complete data; sync.js keeps one job.

Already deep — leave alone

  • engine.js — a pure ~30-function interface powering three hosts (browser, Node tests, Worker verbatim import) with zero adapters; the newly shared validBattle/validStore are exactly the right shape.
  • The sync protocol (server/src/sync.ts) — monotonic revision + 409-with-current-state hides optimistic concurrency behind a tiny interface.
  • server/scripts/dev-node.mjs — one script faithfully faking D1/bundler/static hosting; it earned its keep the day wrangler dev broke.

Top recommendation

Candidate 1 — the battle-constructor in engine.js. Smallest scope of the strong candidates, removes a live divergence risk (undo snapshots built in two places), and every other improvement (facade commands, store owner, server replay) builds on that seam. Candidate 2 is the strategic one; do it second, one duel mode at a time.
